# 研究計画

## 主題

Claude と Jev の役割分担によって、Claude の判断を必要な場面に絞りながら、タスクの成功率を保てるかを調べます。Claude と Jev のどちらかを選ぶ比較ではなく、分担の設計そのものを改善します。

## 問い

1. **RQ1**: Claude の計画の書き方（手順の粒度、入力値の渡し方）を変えると、成功率と Claude の負荷はどう変わるか。
2. **RQ2**: ページの渡し方を変えると、成功率を保ったまま `handoff_chars` をどこまで減らせるか。
3. **RQ3**: 成功した手順を再利用すると、Claude への `handoffs` をどこまで減らせるか。
4. **RQ4**: 失敗した試行のあとに Claude が計画を見直すと、検証済み成功率はどこまで回復し、そのぶん負荷はどれだけ増えるか。

RQ1 から RQ4 まで、すべて現在の基盤で実験できます。RQ2 の手法は「ページの領域」（下）です。

## 設計の変更（2026-11-03）

手順単位の分担から GOAL 単位の分担に変えました。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| Jev の範囲 | 現在の手順だけ。手順ごとに `STEP_DONE` で Claude に戻す | GOAL 全体。サービス情報、計画、ページ、全操作履歴を見てループする |
| 入力文 | 欄ごとに `NEEDS_TEXT` で Claude が書く | Claude が計画時に値を書き、Jev は番号で選ぶ。合う値がなければ `NEEDS_VALUE` |
| 確信度 | 閾値（0.6）未満で `LOW_CONFIDENCE` | 記録のみ |
| 失敗時 | Claude が `act` か `plan` で個別に対処する | Claude が理由を書いて `replan` し、試行を重ねる（既定で最大3回） |
| セッション | 使い捨てのみ | 使い捨て、または専用の保存プロファイル。WSL では Windows 側の Chrome も使える |

以前のログ（`advance`、`STEP_DONE`、`LOW_CONFIDENCE` を含むもの）とは条件が違うため、比べません。下の動作確認の記録は、変更前の設計によるものです。

RQ3 は、同じタスクを手順書なし（`--task NAME`）と手順書あり（`--task NAME --runbook NAME`）で実行して比べます。変える変数は手順書の有無だけにし、手順書は比較の前に `approved` にして固定します。ログの `run_start.runbook.digest` で同じ版であることを確認します。

## ページの領域（RQ2 の手法、2026-11-03）

観測の上限（テキスト 6000 文字、操作 250 件）は、これまで画面内を DOM 順に先頭から切り捨てていました。切り捨てた数は誰にも見えていませんでした。`tasks/fixtures/dense.html`（300 リンクの nav と、47 の選択肢がある select 3つ）では、441 件のうち 191 件が落ち、フォームの操作は1つも残りません。

ページを領域に分けて、要約（位置、表示数と全数）を Claude と Jev に渡します。どの領域を優先するか（`focus`）、外すか（`skip`）は Claude が計画で決めます。学習データ（service.toml の `[[pages.regions]]`、手順書の `focus` / `skip`）が既定値になります。鮮度の判定は view に依存しないので、条件を変えても操作の安全性は変わりません。

変える変数は1つずつにします。

| 実験 | 比べる条件 | 固定するもの |
| --- | --- | --- |
| R2-0 | 変更前の観測 / 要約を足した観測（view なし） | 手順書、パラメータ、`--max-attempts 1` |
| R2-1 | 要約あり view なし / 要約あり view あり（学習した focus / skip） | 同上。手順書は `approved` にして digest を固定 |

view が空のとき、`text` と `actions` が変更前と同じであることは確認済みです（`hotel.html` と `dense.html`、スクロール位置 2つ）。R2-0 で変わるのは、Jev の state の `page.regions`、規則への1文、Claude の `REGIONS` だけです。条件は `run_start.view` で見分けます。

## 実装の移行（2026-11-03）

CLI を Python から TypeScript に移し、`npx webhand` で実行できるようにしました。手順書の保存場所も、ユーザー（`~/.webhand/runbooks`）とプロジェクト（`.webhand/runbooks`）の2か所になりました。実験の変数にしないため、次のものは変えていません。

- Claude が読む出力（`render`、`report`、`describe_plan` など）と、Jev へのリクエスト本文（state と質問）。Python 版の出力を `tests/golden/` に記録し、文字単位で一致することを確かめています（`catalog` だけは、出所の `(project)` / `(user)` を足したため変わっています）
- 観測（`snapshot.js`）と記録（`recorder.js`）。バイト単位で同じです
- Jev への接続は HTTP/2（undici）のままで、リトライは 429/503/529 の最大3回のままです

変わったものもあります。ログの数値で `1.0` が `1` と書かれます。Jev へのリクエストのヘッダーと、実行時間（Node と Python の差）も同じではありません。応答時間（`latency_ms`）や `elapsed_ms` を、この変更の前後で比べるときは注意してください。移行前のログは、Python 版のコミット（`bc1be3d`）のものです。

### 各10回の比較（2026-11-03）

同じ計画で、基準（どちらも外さない）、A、B を1回ずつ順に回し、各10回実行しました。反復のため、Claude の確認は固定の手順にしました。`GOAL_REPORTED` で、ページが Casa Flora かつ「Design · Free cancellation enabled · Destination Lisbon」なら `done`、それ以外は `blocked` で終えます。`JEV_FAILED` なら `run` を1回だけやり直します（今回は0回）。成功判定は `verify()` だけで、30回とも `status` と `verified` は一致しました。ログは `runs/20261103T205117-batch/`（`summary.tsv` に一覧）です。

| 条件 | `verified` | 失敗の形 | 1回目の入力 | 1回あたりの Jev 入力（平均） |
| --- | --- | --- | --- | --- |
| 基準 | 2/10 | 8回とも最初に Casa Flora を開いて `DONE` | 4,966 | 11,641 |
| A `no-offscreen` | 0/10 | 10回とも同じ | 4,715 | 7,204 |
| B `no-not-visible` | 1/10 | 9回とも同じ | 4,752 | 9,242 |

成功した3回は、どれも検索から絞り込みまで手順どおり5回の操作でした。外した版のほうが成功率は高くならず、`offscreen` と `NOT_VISIBLE` はこの失敗の原因ではないと判断します（差は10回では偶然の範囲です）。この計画での `hotel_filter` の成功率は、条件によらず1割前後です。失敗はすべて最初の判断で起きています。一覧に最初から Casa Flora の「View」があり、Jev は最後の手順を先に選んでいます。`runs/20261103T144822/` の成功も、この揺れの範囲で通った1回と考えるのが自然です。

次の候補は、この最初の判断を対象にした実験です。Claude の見直し（RQ4、`--max-attempts 3`）で回復するか、計画の書き方（RQ1、たとえば「検索するまで結果を開かない」を手順に入れる）で成功率が変わるかを、同じく反復して比べます。

## RQ4: 見直しによる回復（hotel_filter、2026-11-03）

上の切り分けと同じ計画で、変える変数を試行の上限だけにしました（`--max-attempts 1` → `3`）。比較元は各10回の比較の基準（2/10、`runs/20261103T205117-batch/`）で、コードも同じです。反復のため、Claude の確認と見直しは固定の手順にしました。GOAL に届いていなければ、ページの表示どおりの理由（Casa Flora を検索と絞り込みの前に開いた。Your filters が Destination anywhere と Free cancellation off のまま）を書いて `replan --restart` します。手順と入力値は変えません。3回目でも届かなければ `blocked` で終えます。ログは `runs/20261103T211017-rq4/` です。

| 項目 | 試行1回（比較元） | 試行3回まで（見直しあり） |
| --- | --- | --- |
| `verified` | 2/10 | **6/10** |
| 1回目の試行での成功 | 2/10 | 2/10 |
| 見直しによる回復率 | — | 4/8（4回とも2回目の試行。3回目での回復は0/4） |
| 成功あたり Jev の呼び出し | 14.0 | 12.3 |
| 成功あたり Jev の入力トークン | 58,203 | 56,038 |
| 成功あたり Claude への戻し | 10.0回、8,040 文字 | 8.0回、5,969 文字 |

- 1回目の試行の結果は比較元と同じ（2/10）で、条件は揃っています。成功率の差は見直しによるものです。
- 回復した4回のうち3回は、2回目の試行でもまず Casa Flora を開き、そこから「Find a stay」で戻って検索と絞り込みをやり直していました。もう1回は最初から手順どおりでした。見直しのメモ（`notes_from_earlier_attempts`）が、開いたあとの立て直しに効いているように見えます。
- 2回目で回復しなかった4回は、3回目も同じ失敗でした。同じ理由を繰り返しても効いていません。理由の書き方を変えるか、手順を変える見直しが必要です。
- 失敗した試行は早く終わるため、成功あたりの負荷は見直しありのほうがわずかに小さくなりました。この結果は、1回目の成功率が低いこのタスクに限ったものです。
- 見直しの理由を固定したので、Claude がその場で書く見直しよりも弱い可能性があります。

### 見直しで手順も書き換える（2026-11-03）

RQ4 と同じ手順で、変える変数を見直しの中身だけにしました。見直しのたびに、同じ理由に加えて `--step` で手順を書き換えます。1つ目を「Do not open any stay yet. | --- | --- | --- |

| 見直しによる回復率 | 4/8（2回目 4/8、3回目 0/4） | **10/10**（2回目 7/10、3回目 3/3） |

## RQ1: 手順の書き方（hotel_filter、2026-11-03）

## 既知の制約

- **Claude のトークンは計測しない。** 対話セッションで動くため、`handoff_chars` は代理指標にすぎない。スキル本文、思考、会話履歴は含まれない。
- **実行者が Claude Code のセッションに依存する。** 履歴や設定の影響を受けるため、多数回の統計を取るときは手順を固定する必要がある。
- **Jev の金額は不明。** API がトークン数のみ返す。
- **確信度は止める条件に使っていない。** 分布は `step.confidence` に残るので、必要になれば実測から閾値を決める。
- **Windows 側の Chrome は WSL の mirrored ネットワークが前提。** NAT のままでは Linux の Chrome に切り替わる。どちらで動いたかは `run_start.chrome_host` に残る。
- **タスクは1件のみ。** ローカルの `hotel_filter` は基盤の検証用で、一般性能の根拠にならない。
- **観測の対象外。** closed shadow DOM、iframe、canvas、ファイルアップロード、新しいタブ、入れ子のスクロールには未対応。

公開スキルからは `--task` の段落と、`finish` の報告にある `verified` を削りました。これは Claude が読む文面の変更なので、実験の変数にあたります。以後の実験は研究用スキル `/webhand-research NAME`（`.claude/skills/webhand-research`）で行います。このスキルは公開スキルに従い、コマンドを `node research/webhand.ts` で呼んで `--task` を渡し、`verified` を報告します。これまでの記録にある `/webhand --task NAME` の実行は、変更前のスキルの文面によるものです。
