# 研究計画

## 主題

Claude と Jev の役割分担によって、Claude の判断を必要な場面に絞りながら、タスクの成功率を保てるかを調べます。Claude と Jev のどちらかを選ぶ比較ではなく、分担の設計そのものを改善します。

## 問い

1. **RQ1**: Claude の計画の書き方（手順の粒度、入力値の渡し方）を変えると、成功率と Claude の負荷はどう変わるか。
2. **RQ2**: ページの渡し方を変えると、成功率を保ったまま `handoff_chars` をどこまで減らせるか。
3. **RQ3**: 成功した手順を再利用すると、Claude への `handoffs` をどこまで減らせるか。
4. **RQ4**: 失敗した試行のあとに Claude が計画を見直すと、検証済み成功率はどこまで回復し、そのぶん負荷はどれだけ増えるか。

現在の基盤で実験できるのは RQ1、RQ3、RQ4 です。RQ2 は手法の実装が必要です。

## 設計の変更（2026-11-03）

手順単位の分担から GOAL 単位の分担に変えました。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| Jev の範囲 | 現在の手順だけ。手順ごとに `STEP_DONE` で Claude に戻す | GOAL 全体。サービス情報、計画、ページ、全操作履歴を見てループする |
| 入力文 | 欄ごとに `NEEDS_TEXT` で Claude が書く | Claude が計画時に値を書き、Jev は番号で選ぶ。合う値がなければ `NEEDS_VALUE` |
| 確信度 | 閾値（0.6）未満で `LOW_CONFIDENCE` | 記録のみ |
| 失敗時 | Claude が `act` か `plan` で個別に対処する | Claude が理由を書いて `replan` し、試行を重ねる（既定で最大3回） |
| セッション | 使い捨てのみ | 使い捨て、または専用の保存プロファイル。WSL では Windows 側の Chrome も使える |

以前のログ（`advance`、`STEP_DONE`、`LOW_CONFIDENCE` を含むもの）とは条件が違うため、比べません。下の動作確認の記録は、変更前の設計によるものです。

RQ3 は、同じタスクを手順書なし（`--task NAME`）と手順書あり（`--task NAME --runbook NAME`）で実行して比べます。変える変数は手順書の有無だけにし、手順書は比較の前に `approved` にして固定します。ログの `run_start.runbook.digest` で同じ版であることを確認します。

## 指標

| 指標 | 定義 | 取得元 |
| --- | --- | --- |
| 検証済み成功率 | `verify()` を通過した実行の割合 | `run_end.verified` |
| 成功あたり handoff 数 | Claude に戻した回数 ÷ 成功数 | `run_end.handoffs` |
| 成功あたり handoff 文字数 | Claude が読んだ文字数 ÷ 成功数 | `run_end.handoff_chars` |
| Jev への委任率 | Jev が決めた操作 ÷ 全操作 | `run_end.decided_by` |
| エスカレーションの内訳 | 理由ごとの回数 | `run_end.escalations` |
| 成功あたり試行回数 | 試行の合計 ÷ 成功数 | `run_end.attempts` |
| 見直しによる回復率 | 2回目以降の試行で検証を通過した実行 ÷ 1回目で GOAL に届かなかった実行 | `run_end.attempt_outcomes` |
| 成功あたり Jev トークン | Jev の全トークン ÷ 成功数 | `run_end.providers` |

失敗実行の値も分子に含めます。

## 実験の条件

- 変える変数は1回の実験につき1つにする。
- 全実行をログに残す。除外する場合は理由を記録する。
- 計画以外を比べる実験では、同じ GOAL、手順、入力値を `start` に渡して揃える。
- RQ4 以外では `--max-attempts 1` にして、見直しの効果を混ぜない。
- 金額ではなく、トークンと文字数で評価する。

## 既知の制約

- **Claude のトークンは計測しない。** 対話セッションで動くため、`handoff_chars` は代理指標にすぎない。スキル本文、思考、会話履歴は含まれない。
- **実行者が Claude Code のセッションに依存する。** 履歴や設定の影響を受けるため、多数回の統計を取るときは手順を固定する必要がある。
- **Jev の金額は不明。** API がトークン数のみ返す。
- **確信度は止める条件に使っていない。** 分布は `step.confidence` に残るので、必要になれば実測から閾値を決める。
- **Windows 側の Chrome は WSL の mirrored ネットワークが前提。** NAT のままでは Linux の Chrome に切り替わる。どちらで動いたかは `run_start.chrome_host` に残る。
- **タスクは1件のみ。** ローカルの `hotel_filter` は基盤の検証用で、一般性能の根拠にならない。
- **観測の対象外。** closed shadow DOM、iframe、canvas、ファイルアップロード、新しいタブ、入れ子のスクロールには未対応。

## 動作確認の記録（2026-11-01）

Claude Code と実際の Jev（`jev-1.14.0`）で `hotel_filter` を1回実行し、独立検証を通過しました。1回だけの動作確認で、成功率の根拠にはなりません。

| 項目 | 値 |
| --- | --- |
| 操作 | 5回（すべて Jev が選択） |
| Jev の呼び出し | 9回（入力 27,503 / 出力 1,751 トークン） |
| Claude への戻し | 9回、7,310 文字 |
| エスカレーション | `STEP_DONE` 4、`NEEDS_TEXT` 1、`LOW_CONFIDENCE` 1 |

`LOW_CONFIDENCE` は `Find stays`（確信度 0.56）で発生し、Claude が承認しました。分担前の Jev 単独実行では、同じタスクで検索を飛ばして `DONE` を申告し、検証に失敗していました。今回は Claude が検索を手順に明記しています。ただし手順4つに対して `STEP_DONE` の確認が毎回発生しており、ここが負荷の主な削減候補です。

## 手順書の動作確認の記録（2026-11-01）

`hotel_filter` を `runbooks/hotel/filter.toml`（ソースコードから作成した draft）で2回実行し、どちらも独立検証を通過しました。各1回の動作確認で、RQ3 の結論にはなりません。

| 項目 | 手順書なし | 手順書あり 1回目 | 手順書あり 2回目（`done_when` 修正後） |
| --- | --- | --- | --- |
| Claude への戻し | 9回、7,310 文字 | 12回、11,159 文字 | 8回、6,645 文字 |
| Jev の呼び出し | 9回 | 10回 | 9回 |
| Jev の入力トークン | 27,503 | 31,597 | 28,315 |
| Jev が選んだ操作 | 5/5 | 4/5 | 5/5 |
| エスカレーション | `STEP_DONE` 4、`NEEDS_TEXT` 1、`LOW_CONFIDENCE` 1 | `STEP_DONE` 6、`NEEDS_TEXT` 1 | `STEP_DONE` 4、`NEEDS_TEXT` 1 |

1回目は `done_when` が「Lisbon の結果が表示される」で、検索前の一覧でも満たされるため、Jev が検索を押さずに完了を申告し続けました。Claude が `act` で補っています。条件を検索後にしか現れない表示（`places in Lisbon`）に直すと解消しました。手順書の完了条件が曖昧だと、なしの場合より悪化することがあります。

## GOAL 単位の動作確認の記録（2026-11-03）

`hotel_filter` を、同じ GOAL、4つの手順、入力値 `Destination=Lisbon`、`--service hotel` で2回実行しました。各1回の動作確認で、成功率の根拠にはなりません。

| 項目 | 1回目（計画は state のみ） | 2回目（計画を各質問の instructions にも入れた） |
| --- | --- | --- |
| 結果 | `blocked`、`verified=False` | `done`、`verified=True` |
| 試行 | 2回（どちらも `GOAL_REPORTED`） | 1回 |
| 操作 | 各試行で `View Casa Flora` の1回のみ | 5回（すべて Jev が選択） |
| Jev の呼び出し | — | 6回（入力 23,138 / 出力 1,354 トークン） |
| Claude への戻し | — | 3回、2,289 文字 |

1回目は、計画を `state.plan` にだけ入れていました。Jev は検索とフィルタを飛ばして Casa Flora を開き、`DONE` を申告しました。`replan --restart` で理由を伝えても、同じ動きを繰り返しました。計画と見直しのメモを各質問の `instructions` にも入れ、「前の手順がページ上で済むまで後の手順に進まない」規則を足すと解消しました。変更前の設計の手順書あり2回目（8回、6,645 文字）と比べて Claude への戻しは減っていますが、条件が違うため比較の根拠にはしません。

## 画面外の要素の動作確認の記録（2026-11-03）

`hotel_reserve` を、記録から学習し直した `hotel-site/reserve`（draft）で3回実行しました。手順書とパラメータは同じで、1回ごとに変数を1つずつ足しています。2回目は Jev の state に `page.offscreen`（画面の上下に残っている量）を足しました。3回目はさらに、対象を選ぶ質問に `NOT_VISIBLE`（必要な要素が一覧にない）を足しました。各1回の動作確認です。

| 項目 | 変更前 | ＋offscreen | ＋NOT_VISIBLE |
| --- | --- | --- | --- |
| `verified` | True | True | True |
| 操作 | 21回 | 15回 | 13回 |
| 朝食バイキングの余分なクリック | 8回 | 2回 | 0回 |
| `NOT_VISIBLE` | — | — | 1回 |
| Jev の呼び出し | 23回（入力 162,169 トークン） | 17回（入力 115,515 トークン） | 16回（入力 109,532 トークン） |

メールアドレスを入力したあと、「予約内容を確認する」は画面の上の外にあり、要素の一覧に入っていませんでした。クリック対象の質問には「該当なし」がないため、Jev は見えている朝食バイキングを選び続けました。切り替えのたびにページが変わるので、`STUCK` も働きません。offscreen を渡すと減りましたが、なくなってはいません（まず下にスクロールしてから、2回クリックしています）。そこまでの2回は、どちらも偶数回の切り替えで、チェックは結果的に残りました。`NOT_VISIBLE` を足すと、Jev は代わりの要素を押さずに「見えていない」と答えました。何も実行されず、次の判断で上にスクロールして、そのまま進みました。
