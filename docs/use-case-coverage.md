# ブラウザ自動化のユースケースと webhand の対応範囲

状態: 2026-11-22 時点の評価。ユースケースの一覧は一般的な知識からの整理（Web 検索はしていない）。対応状況は README、`docs/reference.md`、`docs/design-purpose-skills.md` と実験記録からの読み取りで、実機での再確認はしていない。

## 凡例

- ◎ = 設計も実装もあり、実験で効果を確認済み
- ○ = 実装済みだが、実験は未実施か、効果が確認できていない
- △ = 部分的、または設計だけ
- × = 未対応で予定もない

## 対応範囲の表

| # | ユースケース | 従来手段 | webhand の対応 | 判定 |
|---|---|---|---|---|
| 1 | E2E・回帰テスト（決定的） | Playwright、Cypress、Selenium | `/webhand-regress` は保存した確認の再実行。毎回 LLM が操作するため、決定的テストより遅く、高く、揺れる | △ |
| 2 | 受け入れ条件の確認 | 手動 QA、Gherkin | `/webhand-verify` と `webhand check` | ○ |
| 3 | 探索テスト・モンキーテスト | Monkey、fuzz、手動探索 | `/webhand-explore`。コンソールエラー、5xx、行き止まりを検知し、許可ドメイン外を拒否する | ○ |
| 4 | データ抽出・スクレイピング | Scrapy、requests、BeautifulSoup、Playwright | `/webhand-extract`。表、リスト、リンクを `--read-only` で取る | ○ |
| 5 | 大量・定期の巨大クロール | Scrapy、Crawlee | 設計外。1 ステップごとに LLM を呼ぶ構成で、桁が合わない | × |
| 6 | フォーム入力・申請・予約の代行（RPA） | UiPath、Power Automate、Zapier | `/webhand` と手順書。実行前に同意を取り、変更操作は再試行しない | ○ |
| 7 | 同じ作業のバッチ実行（CSV の各行） | RPA、スクリプト | 未着手（`design-purpose-skills.md` に明記） | × |
| 8 | 定期実行・スケジューラ | cron、GitHub Actions、RPA | 未着手。Claude Code のセッションが前提なので無人運転できない | × |
| 9 | 定点監視・死活監視・変更検知 | Datadog Synthetics、Checkly、Visualping | `/webhand-regress` の差分検知のみ。定期実行がないので監視にならない | △ |
| 10 | 価格・在庫の比較、調査 | クローラ、Perplexity 系 | extract で単発なら可能。複数サイトを横断する仕組みはない | △ |

| 15 | ビジュアル回帰（スクリーンショット比較） | Percy、Chromatic、Playwright | レイアウト崩れの検知は「残る課題」。比較機能なし | × |
| 16 | クロスブラウザ・端末エミュレーション | BrowserStack、Playwright | Chrome 系と実験的な軽量エンジンのみ。Firefox と WebKit は無い | × |

| 21 | 画面と手順の文書化、マニュアル生成 | Scribe、Tango | `/webhand-learn` が録画から手順書を作る。スクリーンショットと文章の成果物は未対応 | △ |

## 厳しい評価

### 1. 実際に差別化できているのは狭い領域だけ

- 「学習してから操作する」という売りの効果は、実験でほとんど確認できていない。
  - 実行方式の比較やケイパビリティモデルの実験では、BU Bench で効果なし。
  - 手順書の学習は +0.080 で、ノイズの範囲内。
  - 他サイトの知識を渡した条件は、渡さない条件に勝てなかった（3/8 対 5/8）。
- 確認できた改善は、ローカルで作ったタスクが中心。
  - 例は `terms_scroll` の 0/8 → 6/8 と、`qty_stepper` の 0/8 → 8/8。
  - 一般化は r39〜r41 で確認できず、そこで打ち切った。
- 評価の弱点は、タスクの作者と改善の作者が同じこと。一般性を示す証拠としては弱い。

### 2. 検証系のスキルは「精度の優位」を示せていない

- 素の `/webhand` に同じ確認を頼んでも、誤 PASS は 0（スキルありも 0）。
- スキルが足すのは報告の形式と規律で、精度ではない。
- 精度で差が出る条件（手順が長いシナリオ、画面に出ない不具合）は「今後の候補」のまま。
- 「決定的テストより優れる」とは言えない。毎回 LLM が操作するので、コスト、速度、再現性で Playwright に負ける。

### 3. 取得と探索は実装中心で、実験が足りない

- extract の実験は一部ある（r58〜r62）。x の成績は 9/10 で、フッター行の誤取得が出た。合計行の問題は未解決。
- explore は実験が一件もない。検出率も誤検知率も不明で、現時点では「動くコード」でしかない。
- 研究方針（変える変数は 1 つ、独立検証）を守っているのは良いが、そのぶん主張できる範囲が狭い。

### 4. 構造的な制約

- **Jev（TypeSafe API）への依存**
  - ページの本文と、ログイン後の画面が外部に送られる。業務利用では、これだけで採用不可になる組織が多い。
  - 単一ベンダーなので、止まれば全部が止まる。
- **Claude Code セッションが前提**
  - API キーも `claude -p` も使わない方針なので、無人実行も CI 実行もできない。
  - 定期実行と大量実行が根本的に塞がっている（表の 5、7、8、9）。
- **操作の選択肢が「観測済み要素の番号」に限られる**
  - 安全性は高いが、Canvas、ドラッグ、ホバー、座標が必要な UI、隠れた要素は扱えない。
  - Jev は数値欄で値を選べないことが、検証実験で分かっている。
- **再試行しない**
  - 変更操作の安全としては正しい。
  - ただしフレークが多い実サイトでは完了率が下がる。実験での取りこぼしの多くが Jev の ATTEMPT_BUDGET だったことと整合する。
- **エンジンの成熟度**
  - Obscura、Lightpanda、Kitesurf は注意書きが多い。実質、検証済みなのは Chrome と headless-shell だけ。
  - Windows Chrome ではダウンロードも使えない。

### 5. 競合との関係

- **Playwright と Cypress**: 決定的で速く無料。webhand が勝てるのは、テストを作る側と、壊れたときに直す側だけ。
- **Browser Use、Operator、Claude in Chrome**: 汎用の自律操作で、利用者数も実績も上。
  - webhand の独自点は、役割分担、安全規律、研究基盤としての厳密さ。ユーザーには見えにくい価値。
- **RPA（UiPath など）**: スケジューラ、バッチ、監査ログ、資格情報の保管庫がある。webhand にはどれもない。

### 総合評価

- **強み**
  - 安全規律（再試行しない、鮮度確認、モデルに入力を出させない）は一貫しており、ユースケース 2、6、11 では説得力がある。
  - 実験の誠実さ（失敗を除外しない、無効だった施策を採用しない）は、研究基盤として非常に良い。
- **弱み**
  - 25 件のうち、実験で裏付けのある ◎ は 0 件、○ は 5 件だけ。
  - 「定期」「大量」「無人」「複数ブラウザ」「視覚」の列は全滅。
  - 実用品としては、「ログインが要る単発の定型作業を、人が見守りながら任せる」という狭い用途にとどまる。

## 優先度の提案

1. explore と extract の実験を先に回す。◎ に上げられるのはここだけ。
2. バッチ実行（params の行を繰り返す）を作る。表の 7 は、実装が小さい割に価値が大きい。
3. 定期実行は後回しにする。方針（API キーなし、Claude Code 前提）と衝突するので、無人化は設計から決める必要がある。
4. ビジュアル回帰、クロスブラウザ、性能、セキュリティは、やらないと明言する。範囲を絞るほうが信頼を得られる。
