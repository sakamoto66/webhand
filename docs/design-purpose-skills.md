# 設計: 目的別スキルの検討

状態: 検討の記録。作業する・検証するは実装済み、取得する・探索するは未着手（取得するは仕様案あり）。個別スキルの仕様は `docs/design-check.md`、`docs/design-regression.md`、`docs/design-extract.md` と各 `skills/*/SKILL.md` にある。

## 目的

webhand はブラウザを操作することに特化している。しかし、操作は目的を達成する手段でしかない。どんな目的のために使われるかで、スキルを分けて考える。0から検討した結果をここに残す。

## 分け方: 出力が何か

目的ごとに、安全の姿勢、合否の根拠、失敗の意味が変わる。そのため「何を出力するか」で分ける。

| 区分 | 出力 | 安全の姿勢 | 合否の根拠 |
| --- | --- | --- | --- |
| 作業する | 副作用（予約、入力、申請） | 実行前に同意、再試行しない | 完了の確認（Claude） |
| 取得する | データ（読むだけ） | 変更操作をしない。最も安全 | 取得値の形式と件数 |
| 検証する | 判定（OK / NG と証拠） | テスト環境。副作用は許容 | 独立した oracle（`DONE` を根拠にしない） |
| 探索する | 発見（不具合の候補と再現手順） | テスト環境に限る | oracle がない。異常を検知する条件が要る |

## 最初に挙がった4案への評価

1. **定型業務を代わりに行う**: よいが新規ではない。いまの `/webhand` と手順書そのもの。「作業する」の核として維持し、一括実行（CSV の行ごとに繰り返す）と定期実行を足す方向で伸ばす。
2. **E2E テストを実行する**: 実行単体のスキルにはしない。毎回 LLM が操作するテストは、遅く、高く、揺れる。Playwright などの決定的なテストに勝てる場面が少ない。webhand が勝つのは、テストを作る側と、壊れたときに直す側。「検証する」に吸収し、保存した確認の回帰実行（`/webhand-regress`）として持つ。
3. **受け入れ条件の確認**: 最も差別化できる。自然言語の条件を、Claude がシナリオと期待に落とし、Jev が操作し、条件ごとに判定と証拠を出す。LLM の得意（解釈）と webhand の分担（Claude が計画と最終判断、Jev が操作）にそのまま合う。
4. **モンキーテスト**: 純ランダムは「Jev は GOAL までの操作を選ぶ」という設計と合わない。Claude が方針（チャーター。例: 「決済フォームに異常な入力を試す」「戻る・再読込を繰り返す」）を与える探索テストにする。操作の記録がそのまま再現手順になる。oracle はコンソールエラー、5xx、行き止まり、レイアウトの崩れなどの異常検知。テスト環境に限る。

E2E と受け入れ確認は、同じ仕組み（条件 → シナリオ → 期待 → 判定）で、モードだけが違う。単発が受け入れ確認、保存して繰り返すのが回帰（E2E）。

## 追加で検討した目的

- **情報を取得する**（抽出、価格比較、調査）: 読むだけで最も安全。抜けていた区分。
- **定点監視**: 手順書と定期実行で、変化の検知や死活確認をする。
- **バグの再現**: バグ報告から再現手順と証拠を作る。受け入れ確認の逆向き。
- **初見ユーザーの試験**: 学習済みと未学習で、目的を達成できるかを測る。webhand の特徴（学んでから操作する）が活きる。研究基盤とも相性がよい。
- **画面と手順の文書化**: `/webhand-learn` の延長（マニュアルやスクリーンショットの生成）。

スキルが増えると description の振り分けが曖昧になるため、初期セットは4つまでにする。

## 「検証する」で分かったこと

実験は、既知の不具合を仕込んだローカルページで行った（`~/webhand-ab` の r48〜r57）。正解はページが実際にすることで、`tasks/` の `verify()` ではない。主指標は、不具合のある条件に PASS を出す率（誤 PASS）。

- 誤 PASS は、`/webhand-verify`、`webhand check`、`/webhand-regress` のどれでも 0 だった。
- 素の `/webhand` に同じ確認を頼んでも、誤 PASS は 0 だった。難しい不具合（1円の切り捨て、送料無料の境界、状態が戻らない、完了画面の金額）でも同じ。精度ではスキルの優位は出ていない。
- スキルが足すのは、報告の形（`PASS` / `FAIL` / `INCONCLUSIVE`、画面の引用、実行した操作）、環境の確認、操作の失敗を製品の失敗にしない規律、期待値を結果を見てから変えない決まり、保存した期待と前回の結果との比較。
- INCONCLUSIVE の原因は、ほぼ操作の失敗だった。次の直しで減らした。
  - 数値欄には、数字をステップに書く（Jev は数値欄で値を選べない）。
  - 前の確認の状態が要る確認は、新しいセッションで操作をやり直す（`replan` は GOAL を変えられない）。
  - 欄を空にするときは `act TYPE_TEXT INDEX --text ""` を使う（空の値は選ばれない）。
- ラウンドの記録（各回の README、`truth.json`、集計）は、リポジトリの外の `~/webhand-ab/rNN/` にある。`docs/research-plan.md` には、これらのラウンドはまだ書いていない。

## 未解決と今後の候補

- **取得する**: 仕様案を `docs/design-extract.md` に書いた（`webhand extract`、`start --read-only`、`/webhand-extract`）。実装と実験が残る。
