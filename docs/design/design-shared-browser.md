# 設計: 共有ブラウザ + セッションごとのコンテキスト

状態: 設計（未実装）。2026-11-15。headless-shell が既定になった後の、並列時のメモリを下げる設計。

## 目的

`--id` で複数のセッションを同時に動かすとき、今はセッションごとにブラウザを1つ起動する。1つのブラウザを共有し、セッションごとに別のコンテキスト（Cookie とストレージが分かれた、メモリ上だけの環境）を持たせて、メモリを下げる。

優先順位は、メモリ使用量、再現性、並列化の順。

非目標:

- 保存プロファイル（`profile:NAME`）、窓つきの Chrome（`--headed`）、Windows の Chrome、Lightpanda、Obscura は変えない。共有の対象は、headless-shell（または `--headless=new` の Chrome）の `--session new` だけ。
- Jev に見せる内容、`snapshot.js`、CLI の出力は変えない。

## 根拠（実測、この WSL、headless-shell）

| 構成 | メモリ（PSS の合計） | 出典 |
|---|---|---|
| 6 セッション、ブラウザ 6 つ（今の方式） | 約 840 MB | E1（同時 6 セッション） |
| 1 ブラウザ + 6 コンテキスト、各 1 ページ | 287 MB | 今回のプローブ（中身の軽い `data:` ページ） |
| 起動フラグを軽くするだけ（GPU、拡張、同期などを止める） | 1 ブラウザあたり 243 → 229〜236 MB（約 3〜6% 減） | 今回のプローブ |

- コンテキストを足すと、1 つあたり約 10 MB。ブラウザを足すと約 140 MB。共有すると、6 セッションで約 66% 減る見込み。
- 起動フラグだけでは足りない。メモリの大部分はブラウザの固定費で、フラグでは動かない。
- ページが軽いので、287 MB は下限寄り。Phase 0（2026-11-15）で実際の fixture を測った: N = 2, 4, 8, 16 で shared は 281、321、414、587 MB、separate は 384、620、1087、2001 MB。

実機で確かめたこと（設計の前提）:

1. Playwright の `browser.newContext()` で作ったコンテキストは、接続を切ると消える。再接続すると、既定の 1 コンテキストと `about:blank` だけになる。webhand はコマンドごとに接続し直すので、そのままでは使えない。
2. 生の CDP で `Target.createBrowserContext {disposeOnDetach: false}` を使うと、接続を切ってもコンテキストとページが残る。`Target.getBrowserContexts` でも見える。
3. Playwright の `connectOverCDP` は、そのコンテキストのページも、すべて `contexts()[0]` の中に並べて見せる。コンテキストごとの区別がつかない。ページ自身の CDP セッションで `Target.getTargetInfo` を呼ぶと、`browserContextId` が分かる。
4. 新しいコンテキストのページのビューポートは、既定のコンテキストと同じ 1120x780（窓の指定が効く）。

## 方式

### 登録簿

ユーザーのレベルに1つ、`~/.webhand/state/shared.json` を置く（権限 0600）。セッションごとの `session-ID.json` とは別。

```
{ "pid": 1234, "port": 40111, "profile": "/tmp/webhand-xxxx", "started": 1789000000,
  "sessions": { "default": "<contextId>", "b": "<contextId>" } }
```

- 登録簿の更新は、短い排他ロック `shared.lock`（pid 入り、死んだプロセスのロックは引き継ぐ。`session.lock()` と同じ作り）の中でだけ行う。
- 登録簿の `pid` が生きていて、ポートに接続できるときだけ「生きている」とみなす。

### 流れ

| 場面 | 処理 |
|---|---|
| `start`（共有を求めた、条件に合う） | ロックを取る。生きた共有ブラウザがなければ起動し、登録簿を書く。生の CDP でコンテキストを作り（`disposeOnDetach: false`）、そこに `about:blank` のページを作る。登録簿の `sessions[id]` と、セッションの状態（`shared: true`、`context_id`、`port`）に書く |
| 以降のコマンド | `Browser.open` が `port` と `context_id` で接続する。自分のコンテキストのページだけを、自分のタブとして扱う（下） |
| `finish`（または `start` の失敗） | ロックを取る。`Target.disposeBrowserContext` で自分のコンテキストを消す。登録簿から外す。最後の1つだったらブラウザを止め、一時プロファイルを消す |
| ブラウザが落ちていた | 共有ブラウザがなくなったことを、明確なエラーで伝える（`SessionError`）。そのセッションは `finish` で片付けて、`start` し直す。他のセッションも同じ |
| 片付けずに終わったセッション | `start` のたびに、登録簿の `sessions` と、状態ファイルのあるセッションを突き合わせる。状態ファイルのないコンテキストは消す（孤児の回収） |

### Browser の変更

- `OpenOptions` に `contextId` を足す。指定があるときだけ、次の変更が働く。ないときは今のまま。
- `openTabs()` を、自分のコンテキストのページだけを返すようにする。自分のページの集合は、接続時に `Target.getTargets`（ブラウザのセッション）の `browserContextId` と、各ページの `Target.getTargetInfo`（今ある `tabId()`）を突き合わせて作る。クリックで開いた新しいタブ（`window.open`、`target=_blank`）は、開いた元と同じコンテキストに作られるので、`observe` のたびに、まだ分類していないページだけを調べて集合に足す。
- `newPage` は使わない。コンテキストを指定した `Target.createTarget` を、`browser.newBrowserCDPSession()` で送り、できたターゲットに対応するページを待つ。
- タブ記憶（`state/tab`）は今のとおり、`targetId` を保存する。
- 生の CDP の小さなクライアント（JSON-RPC を WebSocket で送る）は `src/shared.ts` に置く。Node 22 以上の標準の `WebSocket` を使い、依存は足さない。

### CLI

- `start --share`（新しい opt-in）。既定は off。`WEBHAND_SHARE=1` でも指定できる。
- `--share` が効く条件: エンジンが headless-shell または `chrome` の headless、`--session new`、`--headed` なし。条件に合わないときは、黙って無視せず、理由を示して止める。
- 出力は、`SESSION:` の行に `(shared)` を付ける以外、変えない。
- 既定にするかどうかは、検証（下）の結果で決める。変数を1つずつ変える原則に従い、今回の既定変更（headless-shell）とは別にする。

## ログイン状態の扱い

方針: セッションごとに、独立したログイン状態を持つ。同じログイン状態を使いたいときは、同じセッションの中で、タブを使う。

| 場面 | ログイン状態 |
|---|---|
| 別々のセッション（`--id` が違う、`--session new`） | 独立している。1つのセッションでログインしても、ほかのセッションは匿名のまま |
| 同じセッションの中の複数のタブ（`TAB_n` で切り替える） | 共有される。同じコンテキストなので、同じ Cookie とストレージ |
| クリックで開いた新しいウィンドウ（`target=_blank`、`window.open`） | 開いた元のセッションのコンテキストに入る。同じログイン状態 |
| 保存プロファイル（`profile:NAME`） | 共有ブラウザの対象外。サインインは、そのプロファイルのフォルダに残る。同じプロファイルを2つのセッションで同時に開くことは、今も、これからもできない（同じフォルダを2つのブラウザが開けず、2つ目は `Is profile open in another Chrome window?` で止まる） |

実機で確かめたこと（headless-shell、2つのコンテキストと、Cookie でログインを模すローカルのサイト）:

- コンテキスト A でログインしたあと、A の2つ目のタブは `LOGGED-IN`。コンテキスト B で同じサイトを開くと `ANONYMOUS`。Cookie は漏れない。
- A のページで `target=_blank` のリンクを押すと、新しいページは A のコンテキストに作られた（B にも既定にも作られない）。

エンジンごとの確認（同じ Cookie でログインを模すサイトで、2026-11-15）:

| エンジン | 別々のセッション | 同じセッションのタブ | 同じプロセスの2つ目のコンテキスト | `target=_blank` |
|---|---|---|---|---|
| headless-shell | 独立（コンテキスト A と B） | 共有 | — （共有ブラウザの設計そのもの） | A のコンテキストに新しいページ |
| Chrome `--headless=new` | 独立（同上） | 共有 | — | A のコンテキストに新しいページ |
| Obscura | 独立（プロセスが別） | 共有（複数ページを持てる） | 独立（作れる） | 新しいページは作らず、同じタブでリンク先へ移る |
| Lightpanda | 独立（プロセスが別） | タブを持てない（1ページ） | 作れない | 何も起きない（`window_ignored` を記録） |

- Obscura と Lightpanda は、セッションごとにプロセスが別（常駐プロセスが1つずつ）なので、共有ブラウザの設計は要らず、ログイン状態は、元から独立している。メモリも小さい（23〜33 MB）。
- 「同じログイン状態をタブで使う」は、headless-shell、Chrome、Obscura で成り立つ。Lightpanda では成り立たない（タブを持てない）。ただし Obscura のタブ切り替えは、`tab_form` が通らず、webhand での動作は未確認。

したがって、ログイン済みの状態を複数の作業で使いたいときは、1つのセッションの中でタブを増やし、`TAB_n` で切り替える（今のタブ切り替えの機能のまま）。並列にしたい作業（別々のアカウントなど）は、セッションを分ける。1つのログインを複数のセッションに分け与える機能は、設計に入れない。

## 規則との整合

- 「既定は使い捨てプロファイル」: コンテキストはメモリ上だけで、ディスクに書かない。`finish` で消える。保存プロファイルは共有しない。
- 「保存プロファイルでログインしたページは Jev に送られる」: 保存プロファイルは共有の対象外なので、サインイン済みのページが、ほかのセッションと同じブラウザに入ることはない。
- 「`Browser.act` を経由せず入力しない」「変更操作はリトライしない」: Browser の中身は変えず、タブの絞り込みと作り方だけを変える。
- セキュリティ: コンテキストは Cookie、ストレージ、キャッシュを分けるが、同じブラウザのプロセスにいる。レンダラーの脆弱性を突かれると、理論上は越えられる。サインインしないセッションだけを共有する前提なので、許容できる範囲と判断する。ソケットやファイルは 0600。

## 検証計画（実装の順）

Phase 0（Jev なし、無料）: プロトタイプのスクリプトを `research/` に置く。

- N = 2、4、8、16 で、共有と別々のメモリを、実際の fixture で測る。
- N 個が同時に `observe` したときの所要時間（CPU の競合を見る）。

Phase 1: `src/shared.ts`、`Browser` の `contextId`、登録簿。テストで次を確かめる。

- 隔離: 2 つのコンテキストで、Cookie と localStorage が漏れない（上の実機の確認を、テストにする）。タブの一覧に、他のセッションのタブが出ない。クリックで開いた新しいタブが、開いた元のコンテキストに入る。
- 永続: コマンドをまたいでページが残る。クリックで開いた新しいタブを、自分のものとして扱う。
- 後始末: `finish` で自分のコンテキストだけが消え、最後の1つでブラウザが止まる。CLI を強制終了しても、次の `start` が孤児を回収する。ブラウザを kill したとき、明確なエラーになる。

Phase 2: CLI の `--share`、ドキュメント、既存の golden が変わらないこと。

Phase 3（Jev つき、有料）: 8 つの `--id` セッションを同時に動かし、共有と別々を比べる。

| 指標 | 採用の基準 |
|---|---|
| `verify()` の成功 | 別々と同じ |
| メモリ（N = 8） | 別々の 40% 以下 |
| 全体の所要時間 | 別々の 1.3 倍以内 |
| 他のセッションへの影響 | 漏れがない（隔離テストが通る） |

Phase 4: 基準を満たしたら、既定にするかをユーザーが決める。

## 代替案

| 案 | 判断 |
|---|---|
| A. 起動フラグの削減だけ | 3〜6% しか減らず、足りない。共有と併用はできるが、単独の案にはしない |
| B. Playwright の `newContext()` | 接続を切ると消えるので、不可 |
| C. すべてのセッションを1つの常駐プロセスに（Lightpanda、Obscura と同じ RPC） | メモリは同じく下がるが、`Browser` を常駐側に置く大きな変更で、Chrome の経路にも影響する。共有ブラウザは Chrome が自分でページを保つので、常駐が要らない |
| D. 現状維持 | 8 セッションで約 1.1 GB（シェルの場合。6 セッションの実測 840 MB からの換算）。並列を増やすときの壁になる |

## リスクと未確認

- Playwright が、非既定のコンテキストのページも `contexts()[0]` に並べる挙動に依存する。これは公開された仕様ではない。`playwright-core` は `~1.64.1` に固定してあり、版を上げるときに、隔離テストで確かめる。挙動が変わったら、ページの絞り込みが働かなくなるので、`openTabs` の絞り込みは、挙動に依存しない書き方（ページ自身の `browserContextId`）にしてある。
- 共有ブラウザが落ちると、全セッションが失われる。影響範囲が、セッション1つから、全部に広がる。
- CPU は共有しない前提ではなく、ブラウザの本体のスレッドは共有する。N が大きいとき、遅くなる可能性がある。Phase 0 と Phase 3 で測る。
- 実測は headless-shell だけ。`--headless=new` の Chrome で同じかは未確認。
- 再現性: ネットワークのソケットや DNS のキャッシュは共有される。別々のブラウザより、セッション間の影響が出やすい可能性がある。Phase 3 の `verify()` の一致で見る。
- 孤児の回収は、状態ファイルとの突き合わせに依存する。状態ファイルを手で消されたときの扱いは、Phase 1 のテストで決める。
