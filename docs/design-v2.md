# webhand v2 の設計

Claude と Jev の役割と流れを、0から見直した設計です（2026-11-09）。今の流れと並べて作り、段階ごとにローカルの A/B で確かめます。結果は `docs/research-plan.md` に書きます。

## なぜ見直すか

BU Bench の同じ条件の40セッション（回 `aa`、`aa2`）で、頼まれた作業が最後まで終わったものは0件でした。webhand の側で直せる一番大きな止まり方は「ページには着いたが、必要な操作ができなかった」で、その多くが `STUCK` です。STUCK の29試行のうち、16は Jev が「要る要素が一覧にない」（`NOT_VISIBLE`）と3回答えたもの、7は鮮度チェックで3回断られたもの（`stale`）でした。

今の流れでは、Claude が start/replan で観測の設定（`--read`、`--compare`、`--collect`、`--more`、`--focus`/`--skip`）まで決めます。Jev は、画面に見えている範囲だけを材料に、試行の終わりまで操作を選びます。そのため、ページの理解が足りないまま操作を選び、行き詰まると試行ごと Claude に戻ります。

利用者の方針（2026-11-09）は次のとおりです。

- 一番大事なのは、ブラウザの今のページを正しく理解していること。その理解を、Jev と Claude が判断の材料に使えること。
- 判断した結果と学習データから、次の操作を決める。難しければ利用者に返し、続けるか中止するかを決めてもらう。
- できるだけ Jev が仕事をし、難しいときに Claude へエスカレーションする（部下と上司）。
- iframe、closed shadow DOM など、技術的に取れない部分はいったん諦める。ただし「ここは見えない」とは分かるようにする。

利用者の選んだこと：

- 新しい流れは今の流れと並べて作り、ローカルで新旧を A/B にかけてから切り替える。
- Jev が実行のたびに積み上げるページの知識は、承認なしで次の判断に使う。手順書は今までどおり承認してから使う。
- Claude が難しいと判断したら、状況と選択肢（続ける、別の方法、中止）を AskUserQuestion で返す。

評価の物差しは、頼まれた作業が終わったか（ローカルは `verify()`、BU Bench は `completion.md` と同じ型の分析）です。操作数やトークンの節約は二の次にします。

## 新しい流れ（v2）

### 3つの層

| 層 | 担当 | すること |
| --- | --- | --- |
| ページの理解 | webhand（決定的、毎回） | 今のページを「ページの模型」にまとめる。Jev と Claude は同じ模型を、粒度を変えて読む |
| 操作 | Jev（部下） | 模型と学習データから次の操作を選び、効果を確かめ、知識を積む。難しいときに Claude へ上げる |
| 判断 | Claude（上司） | 目的、到達点、値、許す操作を決める。Jev の相談に指示で答える。完了を確かめる。難しければ利用者に返す |

CLAUDE.md の役割分担（GOAL・計画・値・完了確認・見直し・最終判断は Claude、操作の選択は Jev）と、実行の規則（番号だけを選ばせる、変更操作はリトライしない、`MutationUncertain` で停止、操作の直前の鮮度確認、ページ本文は信頼しない、password は読まない）はそのまま守ります。

### ページの模型（webhand が毎回作る）

1. **ページの状態**：`ready`、`loading`、`blocked`（ボット確認、CAPTCHA）、`login`（ログインが要る）、`error`（HTTP 4xx/5xx、見つからない）、`dialog`（画面を覆うダイアログ）、`empty`（結果0件）。今の `page_check`（`src/agent.ts:61` の `checkPage`、challenge・http_status・title）と snapshot の情報から作ります。
2. **ページ全体の操作の一覧**：画面内だけでなく画面外の要素も、領域ごとに番号つきで載せます。画面外の要素を選んだら、webhand が自動でスクロールしてから操作します。今の画面外の要素の収集（`assets/snapshot.js:290-305`）と `SCROLL_TO`（reveal）を使います。これで `NOT_VISIBLE` の行き止まりを減らします。
3. **一覧**：`ITEMS` / `LIST_END`（`src/browser.ts`）で一覧を自動で見つけます。項目数、続きの操作（ページ送り、もっと見る）も載せます。比べる・集めるは、Claude が付けるフラグではなく、Jev が一覧に対して選べる操作にします。中身は今の `compareScan` / `collectScan` / `loadMore` を使います。
4. **フォーム**：欄、ラベル、今の状態（password の値は読まない）、必須かどうか。
5. **見えない部分**：cross-origin iframe、canvas、closed shadow DOM を「見えない領域」として載せます。中は取りに行きません。
6. **操作の効果**：操作のあと、何が変わったか（アドレス、ダイアログ、一覧、欄の値、変化なし）を短くまとめます。今の `page_changed`（真偽だけ）に代わるものです。

鮮度の確認は操作の直前に必ず行います。ただし、比べる範囲を対象の要素とアドレスに絞り、動き続けるページ（カルーセル、タイマー）でも操作できるようにします。断られたときは、どの部分が変わったかを記録します。

### Jev の1回の判断

1. **今どこか**：Claude の到達点のどれを進めているか。ページの状態は思ったとおりか。学習済みのページと一致するか。
2. **次の操作**：学習済みのページなら、知識（「このページでこの到達点ならこの操作」「この操作でこう変わった」）を先に示し、Jev が選びます。なければ模型の一覧から選びます。どちらも番号だけです。
3. **効果の確認**：思った変化が起きたか。ページの知識に、遷移（操作のラベル → 次のページ、効果）を足します。
4. **相談するとき**：次の場合は、run を止めて `ESCALATE` で Claude に戻します。試行は終わらせません。
   - ページの状態が `blocked`、`login`、`error`、または計画にないページ
   - 選べる操作がない、または Jev の確信度が低い
   - 何回操作しても進まない（今の STUCK に、理由の診断を付けたもの）
   - 計画にない値が要る（今の `NEEDS_VALUE`）
   - 取り消せない操作で、Claude がまだ許していないもの
   - 到達点に着いたと思うので確かめてほしい

### Claude の役目（スキル v2）

- 計画は細かい手順ではなく、目で確かめられる完了条件つきの到達点、値、許す操作にします。観測の設定（`--read`、`--compare`、`--collect`、`--focus` など）は書かせません。
- Jev の相談には、`webhand answer` で短い指示（到達点の直し、値の追加、許可、ページの移動）を返します。run は同じ試行のまま続きます。全体を見直すときだけ `replan` を使います。
- 難しい（ページに着けない、何度相談しても進まない、目的が今のページで成り立たない）と判断したら、AskUserQuestion で利用者に返します。返すのは、ページの状態、どこまで終わったか、止まった理由と、続ける・別の方法・中止の選択肢です。
- 最後に完了を確かめます。うまくいった流れは、手順書の下書き（承認が要る）にします。

### 学習データ

- **ページの知識（承認なしで自動で使う）**：ユーザー側の `~/.webhand/knowledge/<host>/` に置きます。中身は、ページの見分け方（URL の形、題名、領域の並び）、ページの種類、主な操作のラベルと役割、遷移（操作のラベル → 次のページ、効果）だけです。入力した文、クエリの値、個人情報は残しません（`safeUrl` を使う）。
- **サービス情報と手順書**：今の `src/runbook.ts`（`ServiceInfo`、`Runbook`、承認の決まり）をそのまま使います。

## 進み具合

- 段階0: 診断をログに足した（`502e1f4`）。
- 段階1の1つ目: ページ全体の操作と自動スクロール（`start --flow v2`、`4d84cc7`）。15回目で、完了は v1 と同じ 5/5、操作は 61 → 12。
- 段階1の残り: 鮮度の確認の範囲を対象に絞る、ページの状態（`page.status`、`PAGE:` の行）（`750fa6e`）。16回目で、完了は v1 と同じ 5/5、断られた操作は 8 → 0。
- BU Bench で v2 を確かめるため、`start` の流れの既定を環境変数 `WEBHAND_FLOW` で変えられるようにした（`--flow` が優先）。スキルと Claude への指示は v1 と同じままで、bench の `prepare.py` が `BENCH_FLOW` を `launch.sh` に渡す。
- BU Bench の回 `fv1`・`fv2`・`fv1b`・`fv2b`（19組）: 得点も完了も v1 と同じ。「ページ内で必要な操作ができなかった」は 11 → 4 に減った。v2 では Jev がリクエストの大きさの上限で断る回が増えた（HTTP 400）。
- Jev のリクエストを上限の内側に収める（`a2c11d4`、`6daf3b6`）。17回目、18回目で、`catalog_big` の成功は 0/5 → 5/5。
- 段階4: 着けないときに別の入口を試し、だめなら利用者に返す（スキルの第5節と `replan --url`、`418a456`、`67c9ffc`）。19回目で、`item_moved` の成功は 0/5 → 5/5。利用者に返す流れは、まだ試されていない。BU Bench では確かめない。
- 覆われた対象（`4c8f2c9`）: 中央へスクロールし直し、何が覆っているかを Jev に伝える。21回目で、`cookie_wall` の断られた操作は 11 → 2、STUCK は 3 → 0（完了は 5/5 で同じ）。
- 段階5の1つ目: 一覧を最後まで読む（読む画面数の上限 20 → 100、読み取り用のスクロールに鮮度の確認をかけない、`a20de6a`）。22回目で、`collect_long` の成功は 0/5 → 5/5。

## 進め方（段階ごとに A/B）

並べて作るので、v2 は `src/v2/`（新しいモジュール）と `start --flow v2` で切り替えます。今の流れが既定のままです。段階ごとにローカルのタスクで新旧を5回ずつ回し、`verify()` の成功で比べます。評価のスクリプトには `--model claude-sonnet-5-5` を必ず入れます。

| 段階 | 変えるもの | 確かめるタスク（新しく作る） |
| --- | --- | --- |
| 0 | 診断だけ（ログ）：`stale` でどの部分が変わったか、`NOT_VISIBLE` のとき要る要素が画面外の一覧にあったか | 動き続けるページ、画面外の対象（既存の `plan_lowest` など） |
| 1 | ページの模型（状態、ページ全体の操作の一覧と自動スクロール、見えない領域、操作の効果、絞った鮮度の確認） | 画面外のボタン、カルーセルのあるフォーム、ボット確認の模擬ページ、エラーページ |
| 2 | Jev の相談（`ESCALATE`）と `webhand answer`、スキル v2（到達点の計画） | 計画にないページへの寄り道、計画にない値が要るフォーム |
| 3 | ページの知識の積み上げと利用 | 同じサイトで2回目の実行（1回目の知識あり／なし） |
| 4 | 利用者に返す流れ（スキル v2） | 着けないページ（ブロックの模擬）で、選択肢を返すか |
| 5 | 一覧の操作（比べる、集める、続きを読む）を Jev の操作にする | 今の `collect_*`、`plan_*` のタスク |

各段階のあと、`docs/research-plan.md` に結果を書きます。golden（`tests/golden/`）が変わるのは、v2 の state と質問を足すときだけです。そのつど実験の変数として、理由をコミットに書きます。いくつかの段階が揃ったら、BU Bench の大きめの組（40〜60件、Sonnet 5.5 固定）で、頼まれた作業が終わったかを `completion.md` と同じ型の分析で比べます。

## 変更するファイル（主なもの）

- `docs/design-v2.md`（新規）：この設計。最初に書きます。
- `assets/snapshot.js`：ページ全体の操作の一覧、ページの状態、見えない領域、絞った鮮度の鍵。
- `src/browser.ts`：鮮度の確認の診断と範囲、操作の効果のまとめ。
- `src/v2/observe.ts`、`src/v2/loop.ts`、`src/v2/knowledge.ts`（新規）：模型、Jev の判断の流れと相談、ページの知識。
- `src/policies/jev.ts`、`src/policies/base.ts`：v2 の state と質問（今いる到達点、次の操作、相談するか）。
- `src/cli.ts`：`--flow v2`、`ESCALATE` の出力、`answer` コマンド。
- `skills/webhand/SKILL.md`：v2 の節（到達点の計画、相談への答え方、利用者への返し方）。
- `tests/`：段階ごとのテストと golden。新しいタスクは `tasks/`（研究用のリポジトリだけ）に置きます。

## 確かめ方

- 各段階で `npm run check`、`npm test`（Node 24）を通します。有料の API はテストから呼びません。
- 段階0は、ログに診断が出ることをテストで確かめ、CLI の出力と Jev への入力が変わらないこと（golden が同じ）を確かめます。
- 段階1〜5は、新しいタスクを今の流れでは失敗し v2 で成功する形で作り、`~/webhand-ab` の worktree で新旧を5回ずつ（Sonnet 5.5 固定、交互）回して、`verify()` の成功で比べます。
- 最後に BU Bench で、頼まれた作業が終わったかの件数を比べます（完了の分析は別のセッションで、型と件数だけ）。
