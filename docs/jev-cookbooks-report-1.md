## 項目ごとの詳細

### 1 関数呼び出し

**最終評価: 活用できる(実装済み) / 効果 低**(担当 A)

- **レシピの要点**: 自然語の依頼を型付き関数の呼び出しに変える。引数が `Literal` の閉じた集合なら、その値の `Choice` を1問出す。`stated` という Noul を別に置き、「依頼がその引数について何か述べているか」を判定する。述べていなければ引数を省き、関数の既定値を使う。関数の信頼度は各判断の最小値(積ではない)。
- **webhand の現状**: 閉じた集合の Choice はある。`src/policies/jev-questions.ts` の `TYPE_TEXT` 値 Choice は、Claude が渡した値の一覧と `NO_VALUE` を選択肢にする(`jev.ts:356-358`、`jev-questions.ts` の `type_text_value`)。`NO_VALUE` は「どの値も当てはまらない」の役で、`stated` Noul の役をほぼ果たしている。ファイル欄も同じ構造(`jev.ts:361-363`)。対象ごとの `NOT_VISIBLE` もある(`jev-questions.ts` の `criteria.set(NOT_VISIBLE, ...)`)。
- **活用案**: 新しい活用先はほぼない。残る差は、値の一致の信頼度を `NEEDS_VALUE`(`src/agent/outcomes.ts:12`)の判定に使っているかどうかで、これは未確認。
- **担当の判定**: 条件付き(既に大部分が実装済み)
- **担当の効果**: 低。理由は、同じ形が既にあり、差分は確認が必要な小さな点だけだから。webhand の失敗としてこの機構を直接示す記録は見当たらなかった。
- **懸念**: J1(文字どおりの解釈)は、値の説明文が `criteria` に入るとき影響する。AGENTS.md の「モデルには…入力値の番号だけを選ばせる」と整合する。効果が低いので実験はしない。
- **検証方法**: 対象外(効果 低)。

### 3 LLM のガードレール

**最終評価: 条件付き / 効果 低**(担当 A)

- **レシピの要点**: 入力と出力のそれぞれに、危険な内容を調べる Noul を複数並べて1リクエストで評価する。Score で「従うと害がどれだけあるか」も見る。しきい値で pass・review・block・support に振り分ける。ジェイルブレイクの試験で、システムプロンプトより頑健だと示している。
- **webhand の現状**: 入力の検査はない。`src/` に `injection` を扱う箇所はない(`grep -rln injection src` で 0 件)。ページ本文は信頼しないデータという AGENTS.md の規則は、実装では host と Jev の判断に任せられている。読み取り専用と ESCALATE(`src/agent/outcomes.ts:13`、`src/policies/prompts.ts:103`)は、危険な操作の一部を別の仕組みで止める。
- **活用案**: Jev が各ページを見るとき、ページ本文に埋め込まれた指示を検出する Noul を1問足す。その結果が高ければ、そのページの本文をデータとして扱う注意書きを付ける。ただし遮断はしない。
- **担当の判定**: 条件付き
- **担当の効果**: 低(完了率への効果として)。安全性への効果は中かもしれないが、webhand では測っていない。理由は、ガードレールは「依頼が有害か」を判定する部品で、webhand の失敗は有害性ではなく操作の選び違いや見落としが原因だから。ユーザーは完了する作業を優先する。
- **懸念**: J6(敵対的な内容)は、webhand のような敵対的なページに対しては、Noul 1問では効きが不確か。1ステップごとに Jev 呼び出しが増える。AGENTS.md の「計画側は…スキル経由で担う」は、検査の呼び出しにも同じ経路を求める。効果が低いので、実装の優先度は低い。
- **検証方法**: 効果 低 のため対象外とする。安全性を目的にするなら、注入を含むローカル用ページ(`tests/` 用)で検出率を測る。

### 5 LLM の回答を出典と照合

**最終評価: 条件付き / 効果 低**(担当 A)

> 訂正: 担当の効果「中」を「低」に下げた。観測された失敗は verifyClaims の誤判定ではない。また verifyClaims は DONE を最大 2 回差し戻すだけで成功を主張せず、完了確認はホストと verify() に残る(`docs/jev-handoff-conditions.md` の 3 節。このブランチには未収録)。担当が挙げた AGENTS.md との衝突は、確認した範囲では問題と判断しない。

- **レシピの要点**: 回答が与えた段落から導けるかを、Noul 3問(`answerable`・`declines`・`supported`)で1リクエスト判定する。数値を risk(0-1)に直し、0.2 以上をレビューに回す。1000 問での結果は、全件 88.5% 正解、通過分 95.7% 正解。ただし誤答 115 件のうち 31 件は通過している。
- **webhand の現状**: `verifyClaims` は主張ごとに3択の Choice(`MET`・`NOT_MET`・`UNKNOWN`、`src/policies/jev.ts:185-196`、`src/core/types.ts:160`)で判定する。`done` の前に呼ばれ、`NOT_MET` があれば完了を拒否する(`src/agent/index.ts:205-222`)。これは回答の照合と同じ形。
- **活用案**: 主張ごとの3択を、Noul 2-3 問に分ける。「ページがその主張を示すか」「主張と反する表示があるか」を分けて、risk に組み立てる。完了の拒否をしきい値で決める。
- **担当の判定**: 条件付き
- **担当の効果**: 中(推測)。根拠は webhand の完了判定に関する記録がある点。ただし、記録で示された失敗は `check` の NOT_VISIBLE(`webhand check r54-r55`)と、Jev の予算切れ(`webhand regress r56-r57`)で、`verifyClaims` の誤判定ではない。したがって、この変更で改善するという根拠は弱い。
- **懸念**:
  - AGENTS.md の「完了確認はホストエージェント」と衝突しうる。現状は Jev の `verifyClaims` が `DONE` を拒否しており、完了の確認の一部を Jev が担っている(`src/agent/index.ts:205-222`)。この設計が意図どおりかを先に確かめる必要がある。
  - レシピ自身が示すとおり、誤答の一部は通過する(J1・J4 に近い「関連する別の問いへの答え」)。
  - 検証を厳しくすると DONE の拒否が増え、`ATTEMPT_BUDGET` が増える。AGENTS.md の「検証に失敗した方式に合わせてタスクや検証を緩めない」と併せて読むと、比較の方向を決めてから実験する。
  - 効果 中 のため、規模は M。
- **検証方法**: 変えるのは `verifyClaims` の形だけ(3択 Choice と、Noul 2-3問 + しきい値の2通り)。`tasks/` の独立 `verify()` で成否を採点し、DONE の拒否回数と `ATTEMPT_BUDGET` の件数を併せて記録する。`tasks/` を使うので、判定は `verify()` だけで行う。

### 7 簡易メモリ

**最終評価: 条件付き / 効果 低**(担当 A)

> 訂正: 担当の効果「中」を「低」に下げた。r45 は事実なし 5/8、別サイトの事実 3/8(p=0.62)で、両条件とも同じ失敗だった。この候補は変更なしで終了している。古い事実は有害(r35)だが、webhand-learn と「ページを優先する」規則で対応済み。

- **レシピの要点**: 各呼び出しの後に、「依頼と回答を覚える価値があるか」を Noul 1問で判定する。判定は、依頼自体に事実(契約、OS、プランなど)があるかで行い、回答だけにある事実は数えない。保存した記憶は、以後のすべての呼び出しの state に入る。結果は、記憶なしで 3/6、記憶ありで 6/6。
- **webhand の現状**: 2 種類ある。(a) `src/storage/memory.ts` はサイト単位の記憶で、操作の種類と結果をコードで記録する。判定に Jev は使わない。実行が done で終わった操作を、同じ種類のページの `hints()` として提示する。(b) 手順書の `facts: string[]`(`src/storage/runbook/service.ts:29`)は、Claude がログから書く。
- **活用案**: 事実を保存する前、または適用する前に、「この事実はこのサイトについてのものか」を Noul で判定する。レシピでは、保存した記憶が別の状況にも当てはまってしまう問題を、判定の質問で防いでいる。
- **担当の判定**: 条件付き
- **担当の効果**: 中(推測)。根拠は webhand の既知の失敗。`wrong-source facts`(別サイトの事実を使うと 3/8、なしは 5/8、差は雑音の範囲)と、`stale facts`(古い事実)。`runbook learning result` では、完了した実行からの手順書が狭すぎて 4 件中 2 件で使われなかった。Jev の判定で wrong-source を減らせるかは、まだ測っていない。
- **懸念**:
  - AGENTS.md の「手順書とサービス情報に秘密情報、個人情報を書かない」。判定の state にはパスワード欄の値を入れない(AGENTS.md の「password 欄の値は読まない」に従う)。
  - 記憶は増え続ける(レシピ自身が指摘)。
  - 事実は Claude が書いているので、Jev が判定するのは文だけ。J6 の影響は小さいと思われる。
  - 効果 中 のため、規模は M。
- **検証方法**: 変えるのは「保存前に Noul で適用性を判定する」の有無だけ。wrong-source の事実を混ぜたサイトで、事実を使った場合の完了率を比べる。`tasks/` の `verify()` で採点する。

### 8 階層分類

**最終評価: 条件付き / 効果 低**(担当 B)
